# omnilimit specification, version 1

Every omnilimit port must behave as described here. The JSON files in `vectors/` are the
normative test of that behaviour: a port conforms when it passes all vectors for its tier.
They are generated by `tools/gen_vectors.py`, an independent implementation, so no port
validates itself.

## Algorithm

A single algorithm, GCRA expressed as a meter on integers. There is no floating point.

A policy has `limit` (L), `window_ms` (W, at least 1000) and `burst` (B, default L).
Each request adds `W` units, the meter drains `L` units per millisecond, and:

```text
C     = B * W              capacity
drain = ceil(C / L)        time for a full meter to empty

t     = max(now, ts)
lvl   = max(0, level - min(t - ts, drain) * L)

if lvl + W <= C:   level = lvl + W; ts = t; expire after drain; allowed
else:              denied, and nothing is written
```

Public values:

```text
remaining      = floor((C - level) / W)
reset_ms       = ceil(level / L)
retry_after_ms = ceil((lvl + W - C) / L)     denied only
```

- A policy is invalid when any value is not a positive integer, `W < 1000`, or
  `2*B*W + L > 2^53 - 1`. Every intermediate value therefore fits in an IEEE double.
- Ports compute `C` and `drain` once. Store scripts only add, subtract, multiply and compare,
  which is why the same script gives the same answer from any language.
- Denials never write, so a retry storm cannot extend the wait.
- `t = max(now, ts)` means a clock moving backwards never refunds quota.

**Cost.** A request may weigh `k` units instead of one, such as a batch of `k` items. It adds
`k * W` where the formulas above add `W`, in the condition, in the level and in the wait:

```text
if lvl + k*W <= C:   level = lvl + k*W; ...
retry_after_ms = ceil((lvl + k*W - C) / L)     denied only
```

`remaining` is still counted in single units, and a denial still writes nothing. `k` must be an
integer from 1 to `B`: a larger cost could never be allowed, so it is an error and not a
denial. Stores need nothing new for this: they receive `k * W` in place of `W`. A store of
tier `approximate` only counts requests, so it accepts no cost other than 1.

**Peak rate.** This is a rate, not a counter that resets. `5` per minute with burst 5 can admit
`B + L - 1 = 9` requests in one minute. If you need fewer, lower `burst`.

## Policy shorthand

A policy can be written as text, for configuration files and environment variables:

```text
<limit>/<count><unit>      unit = second | minute | hour | day
```

`limit` and the optional `count` (default 1) are decimal integers of 1 to 15 digits with no
leading zero and no sign. `window_ms` is `count` times the unit. Nothing else is accepted: no
spaces, no plurals, no other units, no upper case. So `10/minute` is 10 per 60000 ms, and
`5/15minute` is 5 per 900000 ms. The result is then validated like any other policy. `burst`
has no shorthand: it keeps its default unless given separately.

## Peek and reset

Two operations sit next to the hit. They change nothing above, and stores of tier `exact` and
`local` must support both. An `approximate` store cannot, and the limiter raises a type error
(a configuration mistake, not a store failure) when asked.

**Peek** returns the decision a hit would get now, and never writes:

```text
t     = max(now, ts)
lvl   = max(0, level - min(t - ts, drain) * L)
allowed = lvl + W <= C;    level reported = lvl;    ts reported = stored ts (now if absent)
```

A peek takes a cost like a hit does, and then `allowed = lvl + k*W <= C`.

The public values use the formulas above with `level = lvl`. When allowed, `remaining` therefore
counts the request being asked about, and the effective window is `reset_ms`. A denied peek
equals a denied hit. A peek is advisory: a concurrent hit can take the last unit, so the hit that
follows is still the authority. It neither extends a bucket's expiry nor refreshes its recency.

**Reset** deletes the bucket. The next hit or peek behaves as if it never existed. Resetting a
missing bucket is not an error. A reset that fails or times out is reported as such, and does
not follow `open`/`closed`: no request is being decided.

Together they express a limit that counts only failures, such as a login lockout: peek before
the work and refuse when denied, hit when the work fails, reset when it succeeds.

Sequence vectors mark these steps with `op: "peek"` or `op: "reset"`; a step without `op` is a
hit. Reset steps have no `expect`.

## Refund

A refund gives back a hit that was counted for work that then did not happen, such as a request
cancelled after it was admitted. It is a third operation next to the hit, and like peek and reset
it is part of the `exact` and `local` tiers; an `approximate` store cannot refund, and the
limiter raises a type error when asked.

**Reservation.** A reservation is an allowed hit together with what is needed to undo it: the
key, the cost `k`, and `since`, the timestamp the hit stored (the store's clock at the hit, `ts`
after it). A denied hit wrote nothing, so it is not a reservation and cannot be refunded. Neither
is a decision allowed by `open` after a store failure: nothing was counted.

**Refund** at store time `now`, for a reservation of cost `k` made at `since`:

```text
t     = max(now, ts)                                ts = now if the bucket is absent
lvl   = max(0, level - min(t - ts, drain) * L)
give  = 0                                           if t < since
      = max(0, k*W - min(t - since, drain) * L)     otherwise

if the bucket is absent, lvl = 0 or give = 0:   nothing is written; reports {lvl, ts}
otherwise:   level = max(0, lvl - give); ts = t; expire after drain; reports {level, ts}
```

`give` is what is left of the reservation's own units after the meter drained for `t - since`.
Capping that time at `drain` changes nothing (`k*W <= C <= drain * L`) and keeps every value
below `2^53`. A refund only adds, subtracts, multiplies and compares, like the hit, so the store
scripts need no division. A refund that changes nothing writes nothing, as a denial does.

**Why it is safe.** A refund never leaves a bucket more generous than if the reservation had
never been counted. Compare the real bucket with the one where every other step happened as it
did and the reservation was not counted. Right after the reservation the real level is higher by
`k*W`. A hit that both count adds the same to each, and draining for `d` milliseconds shrinks the
difference by at most `d * L`, because both levels stop at 0. So at `t` the real level is at least
the other one plus `give`, and taking `give` away cannot go below it. This assumes a store clock
that does not go backwards; one that does is still never refunded more than `k*W`. The generator
checks the comparison on every refund it can, by replaying the sequence without the reserved hit.

A bucket that was reset or expired after the reservation no longer holds it:

- When the bucket is absent, or its time is still before `since` (it was recreated by a clock
  that went backwards), nothing is given back.
- Otherwise the reset is not detected. If hits were counted after it, the refund takes up to
  `give` from them, so do not refund a reservation across a reset you made yourself. The
  comparison above does not cover this case.

A reservation is refunded at most once. The limiter spends it when its refund starts, whatever the
outcome, and never retries: a refund that fails or times out may still have been applied, and the
ambiguity resolves to the reservation staying counted. Like a reset, a refund that fails or times
out is reported as such and does not follow `open`/`closed`. A reservation belongs to the limiter
that made it.

Sequence vectors mark these steps with `op: "refund"` and `of`, the index of the earlier hit step
being given back, which was allowed. The cost and `since` (its `state.ts`) come from that step.
`expect` holds `refunded` and, when it is `true`, the `state` the store reported. A second refund
of the same step expects `refunded: false`, without a store call.

Refund is required of `exact` and `local` stores, as peek and reset are: their sequence vectors
include refund steps. The spec version stays 1 because no earlier vector changed meaning. A store
written before refund existed still serves check, peek and reset, and a limiter on it refuses to
reserve with a type error, as it does on an `approximate` store.

## Recipes

A few compositions of check, peek, reset, reserve and refund are common enough to have a fixed
meaning. They add no state and no store operation. `recipe` vectors apply to ports that provide
the recipes.

### Common rules

1. A recipe only calls `peek`, `check`, `reset`, `reserve` and `refund` of the limiters it is
   given. A reserve is a check that keeps its reservation, so the store sees a hit.
2. An entry is a limiter, an id and a cost (default 1). Entries are independent: the same
   limiter and id may appear twice, and each one is peeked and counted on its own. An empty
   list is a value error, raised before any store call.
3. The governing decision of a list `d` of decisions: if any is denied, the denied one with the
   largest `retry_after_ms` (`null` counts as 0), the lowest index on a tie. Otherwise the one
   with the smallest non-null `remaining`, the lowest index on a tie, or `d[0]` if every
   `remaining` is `null`. It is one of the reported decisions, not a copy, and a combined
   result is allowed exactly when its governing decision is.
4. Operations run one at a time in entry order, each finished before the next starts.
5. Each limit follows its own `onStoreError`. An `open` failure is allowed, with reason
   `store_error` and `remaining` `null`, so by rule 3 it never governs over a number. A
   `closed` failure is a denial with `retry_after_ms` 1000 that competes under rule 3 with no
   priority. A failed reset or refund is reported as `false`, follows neither mode, and does
   not stop the resets or refunds after it.
6. Every entry's cost is validated against its limiter before the recipe's first store call.
7. A recipe that peeks raises a type error before any store call if any of its limiters is of
   tier `approximate`. A recipe that reserves raises a type error before any store call if any
   of its limiters cannot refund: every `approximate` one, and one whose store predates refund.
8. Settlement. A pending check (below) settles once, by its first `commit` or `cancel`. It is
   settled before that operation's first store call, so concurrent calls of the same operation
   share its one result. Calling the same operation again returns that result without a store
   call. Calling the other one raises a state error without a store call. This holds for every
   pending, allowed or denied, in either mode.

When several entries break rules 2, 6 or 7, which error is raised is not specified.

### Combined check

A combined check applies an ordered list of entries to one request in two phases. It opens a
pending check, the caller does the work, and then commits or cancels it. A pending reports
`allowed`, the governing `decision`, the `decisions` and `refunded`, which holds one value per
decision: `true` when that entry's reservation was given back, `false` when its refund failed and
it stays counted, and `null` when there was nothing to give back.

**Peek mode** (`peekAll`) is advisory:

1. Peek every entry, in order, without stopping at a denial. Nothing is counted. The pending's
   decisions are all the peeks, the governing decision follows rule 3, and `refunded` is all
   `null`.
2. `commit` on an allowed pending checks every entry, in order, and stops at the first denial.
   The entries after it are not counted, the ones before it stay counted, the decisions end with
   that denial, and it governs. If no check is denied, the result is allowed, its decisions are
   all the checks, and the governing decision follows rule 3. On a denied pending, `commit` makes
   no store call and returns the pending's own result.
3. `cancel` makes no store call, and its `refunded` is all `null`.

**Reserve mode** (`reserveAll`) counts first and gives back what it should not have counted:

1. Reserve every entry, in order, and stop at the first denial.
2. If one is denied, refund the reservations taken before it, in entry order. The pending is
   denied, its decisions end with that denial, and it governs. `refunded` reports each refund,
   and is `null` for the denial and for an entry allowed by `open` after a store failure, which
   counted nothing.
3. Otherwise the pending is allowed, its decisions are all the reservations, the governing
   decision follows rule 3, and `refunded` is all `null`.
4. `commit` makes no store call and returns the pending's own result: the work happened, so the
   reservations stay counted.
5. `cancel` on an allowed pending refunds every reservation, in entry order, and reports each one
   in `refunded`. On a denied pending it makes no store call and returns the pending's
   `refunded`.

Refunds go in entry order like every other operation (rule 4), so the reservation held longest is
given back first. A pending that is never settled keeps what it holds: nothing in peek mode, and
in reserve mode its reservations stay counted, which is the strict side.

`commit` answers with a combined result: `allowed`, the governing `decision` and the `decisions`.
`cancel` answers with `refunded`.

`checkAll` is `peekAll` followed at once by `commit`: it makes the same store calls and gives the
same result.

### Lockout

A lockout counts only failed attempts against one limiter, for an id and a verification:

1. Peek the id. If denied, the verification does not run: the result is not allowed, with that
   denial.
2. Run the verification. If it raises, nothing else is called and the error reaches the caller
   unchanged.
3. If it returns true, reset the id, unless told not to. The result is allowed and verified,
   with the peek's decision.
4. If it returns false, check the id. The result is allowed and not verified, with the check's
   decision. That decision is allowed unless a concurrent attempt took the last unit or the
   store failed `closed`.

### What recipes do not promise

- Atomicity in peek mode. A peek is advisory, so under concurrency `commit` (and `checkAll`) can
  pass every peek, count some entries and then be denied by a later one. The entries already
  counted stay counted.
- Atomicity in reserve mode. Reserve mode is compensated, not atomic: when a later entry denies,
  the earlier ones are counted until their refunds land, about one round trip each. Requests in
  that gap can be denied by them, but none is admitted that a sequence of checks of the admitted
  requests alone would deny, so the error only goes towards denying. A refund that fails leaves
  its entry counted, on the same side.
- Refunds across your own reset. A reservation refunded after you reset its bucket can take back
  units counted after the reset, as described under Refund. Do not reset what a pending in
  reserve mode still holds.
- A bound on verifications. Attempts that overlap can all pass the peek before any of them is
  counted, so a lockout can run the verification more than `burst` times. Each unit freed lets
  through about the attacker's rate times the time between peek and check.

### Recipe vectors

A `recipe` vector names its limiters and runs a `timeline` against them. A step's `at_ms` is
passed to every store call as `now`, and holds for the steps after it until another one sets
it. `fault` makes a limiter's store fail (`error`) or hang (`timeout`) on the listed operations
until `heal`. `expect.calls` is every store call the step made, in order, as `peek`, `hit`,
`reset` or `refund` with the limiter and the id, marked `failed` when the fault answered.
`inspect` reads a bucket's raw state without counting as a call. A combined result gives
`allowed`, the index of the `governing` decision and the `decisions`; a pending adds `refunded`,
and an attempt's adds `verified` and `verify_ran`, with its one decision as `decisions[0]`.
`peek_all` and `reserve_all` open a pending under the name in `handle`, and `commit` and `cancel`
settle the pending of that name; a cancel's result is `{refunded}`. `error` names the kind
raised: `value`, `type`, `state` for a settlement rule 8 refuses, or `verify` for the
verification's own error.

## State format 1

Key: `ol:1:<scope>:<L>-<W>-<B>:<hash>`, where `hash` is the first 32 hex characters of
`SHA-256(salt || 0x00 || id)`, using UTF-8.

- The hash bounds key length and keeps raw IPs out of the store.
- The policy is part of the key, because levels are measured in units of `W`. Changing a limit
  starts a new counter rather than misreading the old one.
- `scope` matches `^[A-Za-z0-9._-]{1,64}$`.

Peek uses `spec/scripts/redis/peek.lua` and `omnilimit_peek_v1` (`spec/scripts/postgres/002_peek.sql`,
which takes no lock). Reset is `DEL` in Redis and `DELETE` in Postgres. Refund uses
`spec/scripts/redis/refund.lua` and `omnilimit_refund_v1` (`spec/scripts/postgres/003_refund.sql`,
which locks the row like the hit); both take `since` after the arguments of the hit.

| Store | Layout | Clock |
|---|---|---|
| Redis, Valkey | Hash `{l, t}` with `PEXPIRE drain` | `TIME` |
| Postgres | `omnilimit_state(key, level, ts_ms, expires_at_ms)` | `clock_timestamp()`, read after the row lock |
| Durable Objects | One object per key: `{level, ts, expiresAt}` | `Date.now()` |

The client's clock is never used, so skew between application servers cannot affect limits.
An injected `now` exists only for conformance vectors; with it, Redis does not set a TTL.

## Tiers

| Tier | Promise | Vectors | Stores |
|---|---|---|---|
| `exact` | Atomic and shared | `sequence`, `concurrency`, `recipe`, plus core kinds | Redis, Valkey, Postgres, Durable Objects |
| `local` | Exact per process; N instances allow about N times the limit | `sequence`, `recipe`, plus core kinds | Memory |
| `approximate` | Only allowed or denied; `remaining` and `reset` are `null` | `contract`, `failure` | Cloudflare rate limit binding |

Every decision reports its tier. Workers KV is not supported: it is not atomic, so it cannot
keep any of these promises.

"Identical" applies to `exact` and `local`. An approximate store follows its provider's model.

## Store failure

A store error, a timeout or a missing binding is a store failure. There is no default policy:
callers must choose `open` or `closed`.

The timeout is the caller's, else the store's own default, else 1000 ms. A store declares a
default only when its normal latency does not fit the general one.

| Mode | allowed | reason | status | Headers |
|---|---|---|---|---|
| `open` | true | `store_error` | none | none |
| `closed` | false | `store_error` | 503 | `Retry-After: 1` |

## Client IP

- `xff` with `hops`: split on commas, trim, take the entry `hops` positions from the right.
  Anything to the left of what your own proxies appended is client controlled.
- A chain with `hops` entries or fewer gives `null`. It never falls back to the first value.
- An invalid value in the chosen position gives `null`.
- IPv4 uses strict decimal octets. IPv6 follows RFC 5952, zone identifiers are rejected, and
  IPv4-mapped addresses become IPv4.
- Masking keeps an IPv6 network prefix (64 bits by default in key helpers). IPv4 is unchanged.

| Preset | Reads | Trust it only if |
|---|---|---|
| `cloudflare` | `CF-Connecting-IP` | The origin only accepts traffic from Cloudflare |
| `cloud-run` | XFF, `hops: 0` | Cloud Run is reached directly |
| `cloud-run-lb` | XFF, `hops: 1` | One Google load balancer is in front |
| `vercel` | `X-Vercel-Forwarded-For` | The app only runs on Vercel |
| `direct` | TCP peer | Nothing proxies the app |

Verify these against your deployment. A preset cannot detect a topology it does not match.

## Headers

Profiles are versioned because the IETF document is still an Internet-Draft.

`draft-11` targets draft-ietf-httpapi-ratelimit-headers-11:

```text
RateLimit-Policy: "<scope>";q=<L>;w=<ceil(W/1000)>
RateLimit: "<scope>";r=<remaining>;t=<ceil(effective/1000)>
```

The effective window is the retry time when denied, the time until the next unit when
`remaining` is 0, and otherwise `reset_ms`. `legacy` sends `X-RateLimit-Limit`,
`X-RateLimit-Remaining` and `X-RateLimit-Reset` (seconds, as a delta). `Retry-After`
(`ceil(retry_after_ms/1000)`) is always sent on denial, in every profile including `none`.

## Vector kinds

| Kind | Tests |
|---|---|
| `sequence` | Decisions, public values, headers and raw state, step by step |
| `key` | Key derivation |
| `ip` | Client IP strategies, canonical form and masking |
| `failure` | Each fault with each failure mode, and a refund that fails |
| `concurrency` | 200 simultaneous hits allow exactly `burst` |
| `contract` | Policy, scope and cost validation, the policy shorthand, and the approximate decision shape |
| `recipe` | Combined checks, pending checks and lockouts: store calls in order, decisions, the governing one, refunds, and errors |

Changing the meaning of a vector requires a new spec version.
